# CPU資源管理の分類と段階分離

基準main: d757ca80709711ad9564898c39902f0fe001c411。

## 第1段階（判断維持）

- 共通だった処理: 山札1枚の価値、手札消費コスト、手札のGP距離、手札入れ替えの機会費用。
- 雲雀に限定されていた共通化対象: 山札残数と手札飽和による追加ドロー抑制、攻撃/重撃後の札温存、最後の防御札温存。
- 固有戦術として残す処理: 連撃の見込みと緑の条件札、射撃/対抗等のカード・キャラ効果、削りの勝利効果、雲雀の防御成功・決着攻撃の加点、旧AIから雲雀ソルバーへの委譲。
- CPU_RESOURCESに共通初期値とデッキ別差分を集約。第1段階では既定演算と計算順を保ち、counterDrawValueは共通関数の互換ラッパーとする。
- 元ソルバーの相手手札サンプリングは内部配列をプールとして使っている。この既存挙動の修正は第1段階に混ぜず、第2段階の非公開情報対策として別途検証する。

第1段階の検証では全10対面・両座席各100seed、計2,000試合について元mainと全操作トークン・勝者・決着理由・ターン・最終状態を照合する。旧AIも全配置の2seedずつ確認する。共通操作列はgzip JSONLに全件保存する。

結果: 2,000試合＋旧AI40試合の全操作・決着・最終状態が一致。第1段階コミットは6803bcb8083777e825159b680f6ad5e0cedc18e7。

## 第2段階（判断変更）

- 全デッキ共通: 今後2回の通常ドローと公開情報から推定する山札破壊圧力を使い、追加ドロー/自己山札消費の機会費用を算出する。
- 手札飽和と攻防の利用可能札不足を追加ドロー利益へ反映。カード消費後の攻撃/防御選択肢減少を共通のspendCostで評価する。
- 同じspendCostを実戦・ロールアウトの重撃札選択に使用。残す手札枚数、最後の専用防御札、決着時の投資例外も同じheavyPolicyを使う。
- 緑/赤の巻物、既知の勝利時ドロー、雲雀の防御時ドロー、回復で戻るLv2の追加ドローを共通drawValueで評価。任意の飛鳥Lv3ドローも同じ関数へ接続する。強制効果の実際の処理は変更しない。
- 柳生の入れ替えは手札効用の差で選び、戻しによる純減0を追加ドローの枯渇コストと混同しない。通常のカード/キャラ効果を再実装しない。
- 初期値は全デッキ共通。雲雀だけ7係数（防御/重撃札の手札ボーナス、攻撃失敗ペナルティ、決着加点、防御成功加点、攻撃後の温存枚数、攻撃重撃予算）を変え、反撃型の姿勢を保つ。他4デッキへの個別例外は作らない。
- ソルバー生成時のresources引数で係数を上書きできる。例: Solver.makeSolver({resources:{horizonTurns:3,normalDrawCost:30}})。通常のサンプリング数24/反復120は変更しない。
- 元ソルバーの内部配列プールを廃止し、公開の固定デッキ構成から公開済みカードを差し引いた未知プールを使う。裏向き攻撃札の正体を読まず、提出前の未知手札に含めてサンプルする。
- 旧経験則AIの独自戦術は残し、緑の巻物の採否と重撃は共通評価へ接続する。大量対戦のA/B比較対象は既定のソルバー。旧経験則AI全体の性能比較は対象外。

注意: Bは共通資源管理に加え、上記の公開情報サンプリング修正も含む。A/Bの差を資源係数だけの因果効果と解釈しない。両者とも同じデッキ同士で戦うA/A対B/Bの比較であり、BがAより絶対的に強いと断言するには別途混合対戦が必要。

## 評価キャッシュ（判断変更なし）

資源関数の反復が高負荷だったため、1判断の中で不変な公開未知プール・札の合法性/役割・仮想手札の選択肢を再利用する。各コントローラ判断と診断用assess/evalBattleの入口で破棄する。カードの合法性関数は元のcanAttack/canDefend/heavyOK/baseUsableをそのまま呼び、仮想手札はfilterで作られた不変配列のみ選択肢キャッシュ対象とする。重撃候補の機会費用も一度だけ計算し、同じ比較値とタイブレークで選ぶ。サンプル数・反復・候補・勝敗計算の省略はない。

キャッシュ前のBは負荷のため1,000試合の記録で中断し、最終Bの集計には混ぜない。キャッシュ前後の200予備seedで全操作SHA256・勝敗・最終状態・全指標が一致した。最終Bが完了した段階で、中断前の1,000件も全件照合する。
